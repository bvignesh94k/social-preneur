Social Preneur: one workspace where every client's posts are planned, approved and dispatched

Architecture for an AI-assisted, multi-client social media operations platform, built for VTurnU Digital Solutions LLP. Design is complete and decisions are confirmed; Phase 0 is next.

!Platform reality check

A correction to my earlier short answer: not every platform is free and open for automated posting. These constraints shape the plan more than any code choice.

X (Twitter)

X's free access, where still offered, has a small monthly post cap shared by every client on the app and almost no analytics. X pricing has changed several times, so the real cap is confirmed at registration. Decision (free APIs only): use free X access while it covers volume. A cap counter tracks posts per month; anything beyond the cap, or everything if free access is unavailable, goes to Assisted mode. At 10 clients posting 3 times a week (about 130 posts a month) this is expected to fit; the ceiling is likely around 30 to 40 active X clients.

LinkedIn company pages

Posting to company pages needs LinkedIn's Community Management API. Access requires an application reviewed by LinkedIn, tied to a registered legal business, and that API product must sit alone on its developer app. The person connecting must hold a page admin role that allows posting.

Meta: Facebook, Instagram, Threads

Needs a Meta developer app, Business Verification and App Review for page posting, Instagram publishing and insights permissions. Instagram publishing only works for Business or Creator accounts, needs media at a public URL (JPEG for images), and has a daily cap on API-published posts per account. Threads has its own API, login and review.

Pinterest

New apps start on Trial access with restrictions. Standard access requires an application with a demo video. Every Pin needs an image or video and a board.

What this means for the plan

Every API used is free: Meta (Facebook, Instagram, Threads), LinkedIn and Pinterest charge nothing for API access, and X runs on free access with an Assisted fallback. Phase 0 includes registering the apps under VTurnU Digital Solutions LLP, publishing a privacy policy, terms and data deletion page on socialpreneur.in, and submitting reviews. The product is designed so every platform works in Assisted mode from day one and switches to API publishing account by account as approvals land. Nothing in the UI claims automation that is not actually running.

03User flows

The monthly cycle is the heartbeat of the product. Every other flow feeds it or recovers from its failures.

The monthly cycle

flowchart TD
  A[Brand Brain ready] --> B[Generate month plan]
  B --> C{Plan health acceptable?}
  C -- No --> B2[Move, replace or regenerate selected slots] --> C
  C -- Yes --> D[Client approves the plan]
  D --> E[Write master caption and platform variants]
  E --> F[Designer works from creative brief]
  F --> G[Internal review]
  G --> H[Client reviews finished posts]
  H -- Changes requested --> E
  H -- Approved --> I[Schedule, preflight checks run]
  I --> J[Publish by API or assisted]
  J --> K[Metrics sync]
  K --> L[Insights shape next month] --> B

Onboarding a new client

  1. Add client: name, logo, website, industry, timezone.
  2. Paste website URL. Crawler reads up to 30 pages and proposes products, services, FAQs and facts.
  3. Review proposals: accept, edit or discard. Nothing enters the Brand Brain unreviewed.
  4. Upload brand guidelines and brochures. Extracted facts join the same review queue.
  5. Mark facts as verified (certifications, numbers, awards).
  6. Add rules: hashtag limit, emoji policy, banned words, weekend posting.
  7. Connect accounts, then assign each discovered page to this client.
  8. Pick a calendar template or set the content mix.
  9. Generate first plan. Invite client approver.

Producing one post

  1. Open a planned slot (status Idea) from the calendar.
  2. Generate content: hook, master caption, CTA, hashtags, alt text.
  3. Platform variants are generated together, each validated against length and hashtag limits.
  4. Claims checker highlights any unsupported number or claim.
  5. Creative brief and design prompt generated; status moves to Design required and a designer is assigned.
  6. Designer uploads creative; media spec check runs per platform (ratio, size, format).
  7. Writer submits for internal review. Reviewer approves or comments.
  8. Post enters client review.

Client approval on mobile

  1. Client receives a review link (in-app now; email or WhatsApp later).
  2. Page shows client logo, then each post as it will appear per platform.
  3. Approve, reject, or request changes with a comment pinned to that version.
  4. Approval stores approver, time, version and content hash.
  5. Team gets a notification; changed posts return to Draft with the comment attached.

Publishing and failure recovery

  1. Approved post is scheduled; one job per account is created.
  2. Preflight runs at schedule time, 24 hours before and 1 hour before: token, permissions, media, approval hash, pause switch.
  3. Problems found early become tasks ("Reconnect Instagram before Thursday 10:00").
  4. At run time the worker publishes and records the platform post link.
  5. On failure the post card shows platform, account, plain-language reason, recommended fix and a Retry button.

The morning routine (Today view)

The manager opens Today and sees, in this order: failed posts, disconnected accounts, posts publishing today, approvals waiting on the team, client change requests, designs due, calendar gaps in the next 14 days, and upcoming relevant special days. Each row has one primary action. Empty sections collapse so the page shrinks as work gets done.

04Database schema

PostgreSQL. Grouped by module, showing key columns only. Full column definitions will live in Drizzle schema files.

Conventions that protect client data

  • IDs: UUIDv7 (time-ordered, index friendly, not guessable).
  • Tenant columns: every tenant row carries agency_id; every client-owned row carries client_id, even when it could be derived through a parent. This makes every query filterable in one step.
  • Composite foreign keys: child rows reference (client_id, id) of their parent, so the database itself rejects attaching Client B's image to Client A's post.
  • Time: timestamptz in UTC; each client has an IANA timezone such as Asia/Kolkata.
  • Deletion: archived_at for business data; hard delete only for drafts and on legal request.
  • Secrets: token columns hold AES-256-GCM ciphertext plus a key version for rotation.

How enforcement works

  • One gate: every server action and route handler starts with requireAccess(session, permission, clientId). It loads membership from the database, never from the request body.
  • Scoped repositories: data access for client-owned tables goes through forClient(ctx), which injects client_id into every query. Raw queries without scope fail code review and a lint rule.
  • IDs are untrusted: a post ID from the browser is always re-checked against the current client scope before use.
  • Database backstop: composite foreign keys stop cross-client links. Postgres Row Level Security on agency_id is added in Version 1.5 as a second wall once multiple agencies exist.
  • AI backstop: the context builder and every assistant tool take the client ID from the server session, never from the model. The model cannot ask for another client's data.
  • Approval links: random 256-bit tokens stored hashed, bound to one client and a scope, expiring (default 14 days), revocable, rate limited, and logged with IP.
  • Isolation test suite: an automated test seeds two clients and calls every registered route as a Client A user against Client B IDs. Any non-refusal fails the build.

07Integration architecture

Each platform is an adapter behind one interface. The rest of the product never knows which platform it is talking to, only what that platform can do.

interface PlatformAdapter {
  platform: Platform
  capabilities: Capabilities            // formats, caption and media limits, analytics fields
  authorizeUrl(state: string, pkce: Pkce): URL
  exchangeCode(code: string, pkce: Pkce): Promise<TokenSet>
  refresh(conn: OAuthConnection): Promise<TokenSet | NotRefreshable>
  discoverAccounts(conn: OAuthConnection): Promise<RemoteAccount[]>
  checkHealth(account: SocialAccount): Promise<HealthReport>   // token valid, scopes, role on page
  validate(variant: Variant, media: Asset[]): Issue[]
  publishStep(job: Job, step: Step): Promise<StepResult>       // resumable, records platform object ids

Connection lifecycle

  1. Start: user clicks Connect on a client's Accounts page. Server creates a signed state bound to user, client and platform, plus a PKCE verifier.
  2. Callback: state verified, code exchanged server-side, tokens encrypted immediately. Granted scopes compared with required scopes.
  3. Discover and assign: all pages or profiles the login can manage are listed. The user ticks the ones that belong to this client. Pages already assigned to another client are shown locked with that client's name.
  4. Health check: adapter confirms it can read the account and has publishing permission. Only then is the status set to Connected.
  5. Refresh sweeper (daily): refreshes tokens expiring within 10 days where the platform allows; short-lived X tokens refresh just before use.
  6. Deauthorization: platform callbacks and failed refreshes mark accounts Disconnected, pause their jobs, and notify owners.

Media handling

  • Browser uploads straight to storage through a signed URL, so large videos never pass through the app server.
  • Images are converted and resized in the browser before upload (for example PNG to JPEG for Instagram), so no image server is needed.
  • At publish time the worker gives platforms a short-lived signed URL to fetch media. Storage with no egress fees keeps this free.

08AI architecture

AI is a tool the product calls through one gateway, never a component with direct database access. The gateway decides which model runs, what context it gets, what it may claim, and what it costs.

The gateway

  2  Route model           feature → tier → provider and model (editable in settings)
  3  Build context         layered, cached, client-scoped (below)

Guardrails that run on every output

  • Claims checker: detects numbers, percentages, years in business, "certified", "award", "leading", "#1", quotes and client results. Each must match a verified fact, or the phrase is highlighted as "Needs confirmation" and a safe rewording is offered.
  • Brand rules: hard rules (max hashtags, no emojis, banned words, required website link) are validated in code after generation, not just requested in the prompt.
  • Platform limits: character counts and hashtag counts checked per variant.
  • House style: em dashes and spaced en dashes replaced with commas or colons by a deterministic sanitizer, covered by a unit test.
  • Brand Brain protection: AI output can only create brand_suggestions; it has no write path to the profile itself.

Similarity and repetition

Embeddings of title, hook and concept are stored per client in pgvector. A new idea is compared only with the same client's ideas, scheduled posts and published posts. Result: similarity score, the three closest posts with dates, and a label such as Similar content was posted 18 days ago. A "fresh angle" rewrite is generated only when the user asks, which saves a call on every warning. Thresholds are tuned on demo data in Phase 3.

Cost control

  • Two model tiers: a fast, inexpensive model for most work and a stronger model for monthly planning and report narratives. Mapping is editable without code changes.
  • Stable prompt prefix per client for provider-side prompt caching.
  • Embeddings from a low-cost model, computed once per item and reused (text hash prevents recomputation).
  • Batching: one call for a whole month's slot fill; one call for all platform variants.
  • Hard monthly caps per agency and client, with an alert at 80 percent.
  • Prompt templates versioned in the repository and checked against a small evaluation set of demo clients before changes ship.
Decision: OpenAI as default provider

A paid OpenAI API key (prepaid $5 credit) is the default for generation and embeddings. Paid API data is not used for model training by default, so real client brand documents can be used. Models per tier are chosen from OpenAI's current lineup at build time and stay editable in settings. Two budget walls: a monthly limit on the OpenAI project dashboard, and the app's own caps in ai_budgets.

Rough AI cost at 10 clients: about 1,000 AI calls a month (plans, ideas, content, rewrites). With a small, low-cost model doing most work, $5 of credit is expected to last several weeks at minimum; Tamil generation uses more tokens and costs more. This is an estimate; the Usage page reports real spend, split by language, from ai_runs from the first day.

English and Tamil

  • Language per post: English, Tamil, or bilingual captions, with a default language per client in the Brand Brain.
  • Consistent Tamil wording: each client stores Tamil brand vocabulary (product names, preferred terms, words to avoid) that the AI must follow.
  • Similarity: a multilingual embedding model, so an English post and a Tamil post on the same topic are recognised as related.
  • Counting: character limits counted the way each platform counts. One visible Tamil letter is often 2 to 3 characters to a platform.
  • Special days: Tamil Nadu observances included (Pongal, Tamil New Year, Aadi Perukku, Karthigai Deepam and others), suggested only where relevant to the client.
  • Creative briefs: Tamil-capable font suggestions such as Noto Sans Tamil or Mukta Malar.
  • Interface: English for now; all UI text goes through a message catalog so a Tamil interface can be added later.

09Scheduling and publishing

The database is the source of truth for every job. The queue only delivers work. If the queue loses a message or delivers it twice, the database state still prevents a missed or duplicate post.

Job lifecycle

stateDiagram-v2
  [*] --> Pending
  Pending --> Queued: due within 2 minutes
  Pending --> Cancelled: unscheduled or paused
  Queued --> Processing: lease claimed
  Processing --> Published: platform confirmed
  Processing --> Retrying: safe to retry
  Retrying --> Queued: backoff elapsed
  Processing --> NeedsVerification: result unknown
  NeedsVerification --> Published: found on platform
  NeedsVerification --> Queued: confirmed not posted
  Processing --> Failed: not retryable
  Retrying --> Failed: attempts used or late window passed
  Failed --> Queued: user fixed and retried
  Published --> [*]

How a post goes out

  1. Schedule: for an approved post, one job is created per target account. publish_key = hash of variant ID, account ID and approved version. A unique index makes a second job for the same thing impossible.
  2. Tick: a cron trigger runs every minute and moves jobs due in the next 2 minutes from Pending to Queued, sending each to the queue with the exact delay.
  3. Claim: the consumer runs one atomic update: set Processing and a 5 minute lease, only if the job is still Queued or Retrying. A duplicate delivery finds nothing to claim and exits.
  4. Final preflight: pause switches off, account healthy, approved version still current, content hash unchanged, within the late window, rate limit available.
  5. Publish in steps: an attempt row is written before each external call. Multi-step platforms (Instagram creates a container, waits for processing, then publishes) store each platform object ID, so a retry resumes rather than restarts.
  6. Confirm: store platform post ID and link, set Published, update post status, notify owner, schedule metric syncs at 1 hour, 24 hours, 7 days and 28 days.
  7. Recover: a sweeper returns expired leases to Queued if no request was sent, or to Needs verification if a request may have reached the platform.

Assisted publishing

Assisted jobs follow the same lifecycle, but at run time they notify the owner instead of calling an API. Things free tiers do not give you

  • Backups: free database tiers offer little or no restore history. The nightly encrypted dump to R2 is part of Phase 0, with a restore drill before launch.
  • Storage headroom: images for 10 clients use roughly half a gigabyte a month; video uses far more. Archived creatives older than 12 months move to a cheaper storage class.

  • Required public pages: privacy policy, terms of service and a data deletion page on your domain. All platform reviews ask for them.
